# cgpt-bridge — Chrome Extension

The Chrome MV3 extension of `cgpt-bridge`. It is the router between the Rust native host and ChatGPT: it receives requests from the host (`ask`, `stop`, `status`, `ping`) over Chrome Native Messaging, runs them in a ChatGPT tab through the content script (insert a prompt, submit it, wait for the assistant response) and returns the text. CLI asks use your active ChatGPT tab; gateway asks use the extension's own ChatGPT window. The toolbar icon sends a hardcoded test prompt only when the developer flag `devTestAsk` is set (see "Manual test").

The agent protocol, command execution and the Rust CLI are not part of the extension (see `../docs/architecture.md`).

## Layout

```
extension/
  manifest.json
  package.json
  tsconfig.json
  vite.config.ts
  scripts/
    copy-manifest.mjs
  src/
    background.ts       # service worker; starts the bridge, handles action click
    bridge.ts           # persistent Native Messaging bridge: host requests -> tabs
    nativeHost.ts       # the registered native host name
    targetTab.ts        # which tab / window a request runs in
    askControl.ts       # stop and cancel of a running ask
    content.ts          # routes messages, calls the adapter
    chatgptAdapter.ts   # ChatGPT-specific DOM logic (selectors, composer, answer wait)
    pageShim.ts         # page-world shim: tees the answer stream while an ask runs
    sseParser.ts        # parses that stream (ChatGPT's stream format lives here too)
    bridgeProtocol.ts   # internal extension message types
    errors.ts           # typed error classes + serialization helper
  dist/                 # built output (generated by `npm run build`)
```

The principle from `docs/architecture.md` applies: ChatGPT-specific selectors and DOM behavior are confined to `chatgptAdapter.ts`, so a UI break is a one-file fix. The knowledge of ChatGPT's answer stream (endpoint and event format) is the one exception: it sits in `pageShim.ts` and `sseParser.ts`.

## Install dependencies

Requires Node.js 20.19+ or 22.12+ (vite 8) and npm.

```sh
cd extension
npm install
```

## Build

```sh
npm run build
```

The build runs Vite twice (once for the background service worker, once for the content script) and copies `manifest.json` into `dist/`. The output is a self-contained unpacked extension at `extension/dist/`.

Other scripts:

- `npm run typecheck` — strict TypeScript check, no emit.
- `npm run test` — unit tests for pure logic (`test/*.test.ts`): bundled with esbuild, run with `node:test`.
- `npm run clean` — remove `dist/`.

## Load the unpacked extension in Chrome

1. `cd extension && npm install && npm run build`
2. Open Chrome and go to `chrome://extensions`.
3. Enable **Developer mode** (toggle in the top-right).
4. Click **Load unpacked**.
5. Select `extension/dist/`.
6. The extension id is fixed: `manifest.json` carries a `key`, so the id is always `oplkebjcjmifidmnbehpadfakodjjoge` and the installers write it into the native messaging manifest's `allowed_origins`. There is nothing to copy from `chrome://extensions`.

## Manual test

1. Open `https://chatgpt.com/` in Chrome and log in.
2. No need to reload the ChatGPT tab after installing, updating or reloading the extension. Chrome does not inject content scripts into pages that were already open, so the extension does it itself (the `scripting` permission): into every open ChatGPT tab when it is installed or updated, and into a tab that does not answer when a request goes to it, once, before sending that request again. If even that fails, the error names the tab (its title and address) and asks you to reload it.
3. Turn the developer flag on: in the service-worker console (see "Inspect logs") run `chrome.storage.local.set({ devTestAsk: true })`. Without the flag a click on the `cgpt-bridge` toolbar icon only logs a line and sends nothing to ChatGPT. Then click the icon.
4. Watch the badge:
   - `...` while the test prompt is in flight.
   - `OK` on success.
   - `ERR` on failure.
5. Inspect the service-worker console (see below) for the assistant response text.

The hardcoded test prompt is `Say "pong" in one short sentence.` (defined in `src/background.ts`).

## Inspect logs

### Background service worker console

1. `chrome://extensions` → find `cgpt-bridge`.
2. Click the **service worker** link (visible while the worker is alive; it may say `Inactive` — click to wake it).
3. A DevTools window opens. Use the **Console** tab.

Look for lines prefixed with `[cgpt-bridge]`.

### Content script console

1. Open `https://chatgpt.com/` and right-click → **Inspect** to open the page DevTools.
2. The content script's `console.*` output appears in the page's regular Console tab.

The current content script does not log on its own; errors are surfaced back to the background worker via the response message.

## Known limitations

- **ChatGPT DOM can change without notice.** ChatGPT serves several markups at once (signed-in app, the newer "octane" front-end, the older "classic" one). The adapter detects which one is live (`detectProfile()`), accepts all of them, and fails fast with `answer_not_detected` → `dom_failure` (plus a one-line DOM summary) when it sees no reply 30 s after submit, or when the answer stream ended without answer text and the page shows no answer 3 s later (once it stops generating). `answer_not_detected` is a failure of the page markup or of the stream (an error inside it, moderation, an answer that is not text), not of the chat. `target_mismatch` is the other failure: a gateway ask (it names its chat), or a CLI ask sent from a saved chat (the chat it was sent from), found the page showing another chat than its own, before the prompt was sent, for longer than 3 s while the answer was awaited (a deleted chat sends the tab to `/`), or when the answer was read. A CLI ask that starts a new chat is not watched this way. When the stream ended without answer text in a saved chat that the page had left, the ask fails as `target_mismatch`, not `answer_not_detected`; a new-chat ask on a page whose markup drifted stays `answer_not_detected`. Neither is a stop: after `target_mismatch` nothing is stopped, because what generates now is the user's other chat. Both reach the host as `dom_failure` and the CLI as exit code 6. When a refresh breaks things, repair in `src/chatgptAdapter.ts`; do not spread selectors elsewhere. `src/pageShim.ts` is dormant except while a bridge request is in flight.
- **The toolbar click is a test, off by default.** With `chrome.storage.local.devTestAsk === true` it sends a hardcoded prompt to the active ChatGPT tab; otherwise it only logs; real asks come from the native host (`cgpt ask`, the gateway).
- **No agent protocol.** No `cgpt-agent-response-v1` parsing, no plan storage, no command execution: those live in the CLI.
- **Hardcoded test prompt.** Defined in `src/background.ts`. Editing the prompt requires a rebuild.
- **Nothing is written to disk by the extension** and nothing is sent anywhere off-machine; the toolbar test only logs to the console (in `chrome.storage.local` it reads the `devTestAsk` flag and keeps `chatgptProjectIds`, the ChatGPT project ids it found or created, by project name).
- **ChatGPT projects.** A new chat of an ask that names a `project` goes into the ChatGPT project of that name, found by its sidebar row (`data-app-action-sidebar-project-*` attributes, labels compared in NFC) or created through the sidebar's create dialog; the project's id is then remembered per name in `chrome.storage.local` (key `chatgptProjectIds`), and the gateway's tab loads a remembered project's page directly; a CLI ask only looks for its row, and when no row is in view it creates the project again. When nothing works within 30 s, the chat is a plain new chat and the answer carries a `warning`. Nothing is clicked to open a collapsed "Projects" section: a project it hides and that is not yet remembered gets a duplicate. A long list shows the five newest projects and a "show more" control: when the row is not in view it is pressed once and the list is watched until it stops growing.
- **Existing tabs must be reloaded** after installing/reloading the extension before the content script is injected.
- **Single active-tab assumption.** The action only targets the currently active tab in the focused window.
- **No clipboard, ever.** The composer is populated by direct DOM updates and dispatched input events.
